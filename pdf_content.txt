Analisa Coding Aplikasi Rental Mobil  
1. Ringkasan Umum  
Apakah implementasi sudah sesuai dengan temuan analisa?  
Secara garis besar: Ya, sebagian besar sesuai , namun ada beberapa gap kritis terutama pada 
implementasi RAG yang seharusnya menjadi inti sistem.  
Teknologi yang Ditemukan:  
• Backend:  Laravel (PHP) — terlihat dari struktur app/Http/Controllers , routes/web.php , models , 
migrations , config  
• Database:  MySQL ( if0_41735785_rental_mobil  di sql212.infinityfree.com ), SQLite lokal  
• AI/RAG Engine:  Python Flask eksternal di https://iZikra -iZikraSpaces.hf.space  (via env 
RAG_ENGINE_URL ) 
• Session:  File-based (tidak Redis di production)  
• Frontend:  Blade templates + Vanilla JS (tidak ada React/Vue)  
Gap Terbesar:  
RAG retrieval yang sesungguhnya (vector similarity search via ChromaDB) tidak terlihat di kode 
Laravel. Yang terjadi adalah context injection dari MySQL ke prompt LLM  — ini lebih tepat 
disebut prompt engineering dengan context  bukan RAG sungguhan.

4. Poin yang Belum / Belum Sepenuhnya Diselesaikan  
4.1 RAG Retrieval Sejati dengan ChromaDB (KRUSIAL)  
Masalah:  Kode Laravel hanya membangun contextData  string dari MySQL dan mengirimnya ke service 
Flask ( RAG_ENGINE_URL ). Tidak ada kode yang secara eksplisit:  
• Menghubungi ChromaDB instance  
• Memanggil collection.query()  dengan query_embeddings  
• Melakukan vector similarity search  
• Mengambil dokumen dari ChromaDB berdasarkan skor kemiripan  
Bukti tidak langsung:  
• File .env: RAG_ENGINE_URL=https://iZikra -iZikraSpaces.hf.space  — ini adalah service HF Spaces, bukan 
ChromaDB langsung  
• Tidak ada konfigurasi CHROMA_*  env variables  
• Tidak ada library ChromaPHP atau chromadb client di vendor/  (tidak bisa diverifikasi dari luar, 
tapi tidak ada require di composer.json ) 
Implikasinya:  Apa yang disebut "RAG" saat ini adalah in-context learning  — menyisipkan data 
MySQL sebagai konteks prompt ke LLM. Ini BUKAN RAG sejati karena tidak ada retrieval berbasis 
vector similarity.  
File yang seharusnya ada (jika RAG benar):  
• Konfigurasi ChromaDB client di Laravel  
• Fungsi chroma_client = chromadb.HttpClient(...)  
• collection.query(query_embeddings=[...], n_results=5, where={"rental_id": ...})  
• Penggabungan hasil ChromaDB + MySQL (hybrid)  
 
 
 
4.2 Metadata Filtering di ChromaDB  
Even if ChromaDB were queried, filtering by rental_id  and kota at the vector search level is not 
implemented. The where  clause in ChromaDB query would be needed for true multi -tenant RAG.  
 
4.3 Hybrid Retrieval (Vector + Keyword)  
True hybrid retrieval would require:  
1. Vector search: collection.query(query_embeddings=[...])  → ChromaDB  
2. Keyword search: BM25 / TF -IDF pada document store  
3. RRF (Reciprocal Rank Fusion) untuk menggabungkan hasil  
Tidak ada evidence ini di kode Laravel maupun konfigurasi.  
 
4.4 Knowledge Base untuk SOP/Denda/Harga  
Tidak ada folder storage/app/public/documents  atau storage/app/private/knowledge  yang terdeteksi. Tidak 
ada file SOP, daftar harga, syarat sewa, atau matriks denda yang termuat dalam sistem.  
Implikasi: Chatbot yang menjawab pertanyaan tentang denda, SOP, atau harga kemungkinan besar 
mengandalkan pengetahuan LLM saja  ( parametric knowledge), bukan dari knowledge base 
retrieval.  
 
5. Saran Perbaikan  
Prioritas 1 — Perbaiki RAG Implementation (Jika Ini Skripsi)  
File yang perlu diubah:  Butuh akses ke kode Flask service di HuggingFace Spaces untuk 
diperbaiki. Jika itu di bawah kontrol, berikut yang harus ditambahkan:  
1. Di Flask service ( app.py atau rag_engine.py):  
import chromadb  
from chromadb.utils import embedding_functions  
 
chroma_client = chromadb.HttpClient(  
    host=os.getenv('CHROMA_HOST', 'localhost'),  
    port=int(os.getenv('CHROMA_PORT', 8000))  
) 
collection = chroma_client.get_collection("rental_knowledge")  
 
def retrieve_context(query: str, rental_id: str = None, top_k: int = 5):  
    # 1. Vector search  
    vector_results = collection.query(  
        query_texts=[query],  
        n_results=top_k,  
        where={"rental_id": rental_id} if rental_id else None  
    ) 
    # 2. Keyword search (BM25)  
    keyword_results = bm25_search(query, top_k)  
    # 3. Hybrid fusion (RRF)  
    fused = reciprocal_rank_fusion([vector_results, keyword_results])  
    return fused  
 
2. Di Laravel ( ChatbotController.php):  
o Endpoint /chat  harus mendapatkan hasil retrieval dari ChromaDB, bukan hanya context 
string MySQL  
o Kirim query_embedding  atau biarkan Flask yang generating embed di server  
Catatan:  Saat ini HuggingFace Spaces digunakan sebagai endpoint tunggal — jika Spaces tersebut 
melakukan query ke ChromaDB sendiri, maka verifikasinya butuh akses ke kode Spaces.

Jika aplikasi benar -benar ingin memiliki RAG dengan knowledge base:  
1. Buat folder storage/app/private/knowledge/  atau storage/app/public/documents/  
2. Buat script ingestion:  
// database/migrations/..._ingest_knowledge_base.php  
// Loop semua file .txt/.pdf di folder knowledge  
// Chunk dokumen → embed → store ke ChromaDB  
 
3. Jenis dokumen: SOPRental.txt, DaftarHarga.txt, SyaratKetentuan.txt, Denda.txt  
4. Metadata ChromaDB: {rental_id, doc_type, kota}

• Tambah query builder whereBetween('created_at', [...])  untuk filtering historis

6. Kesimpulan Akhir  
Apakah aplikasi sudah layak dianggap implementasi skripsi yang sesuai?  
Secara struktural: Ya  — aplikasi memiliki arsitektur yang cukup lengkap untuk skripsi dengan 
topik Rental Mobil + AI Chatbot.  
Secara teknis RAG: Belum sepenuhnya  — istilah "RAG" yang dipakai dalam temuan analisa 
belum terealisasi secara sesungguhnya. Yang ada saat ini adalah:  
• In-context learning  (menyisipkan data MySQL sebagai prompt context)  
• Bukan retrieval -augmented generation  karena tidak ada vector similarity search yang 
confirmed  
Bagian Paling Krusial untuk Segera Diperbaiki  
1. Verifikasi service Flask di HuggingFace Spaces  — Apakah benar -benar melakukan 
ChromaDB query? Jika tidak, ini harus diperbaiki di sisi Spaces. Kode Flask harus melakukan 
collection.query()  dengan embeddings.  
2. Knowledge base documents  — Jika aplikasi mengklaim memiliki "RAG -based chatbot", 
maka knowledge base SOP/harga/denda harus ada sebagai dokumen yang di -ingest ke 
ChromaDB. Tanpa ini, chatbot tidak bisa menjawab pertanyaan spesifik tentang denda/SOP 
secara akurat.  
3. Multi -tenant filtering di level ChromaDB  — Saat ini filtering rental_id  dan kota dilakukan di 
MySQL. Untuk RAG sejati, metadata filtering juga harus dilakukan saat vector search di 
ChromaDB agar tenant isolation terjaga di level retrieval.
